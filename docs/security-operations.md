# Security Operations

## 1. 보안 구성 개요

이 실습에서는 AWS 리소스에 대한 네트워크 접근을 제어하는 Security Group과 AWS API 및 리소스 관리 권한을 제어하는 IAM을 구분하여 사용한다.

두 기능은 서로 다른 계층에서 작동한다.

| 구분 | Security Group | IAM |
|---|---|---|
| 목적 | EC2로 들어오고 나가는 네트워크 트래픽 제어 | AWS 리소스 및 API 작업 권한 제어 |
| 제어 대상 | IP 주소, 프로토콜, 포트 | 사용자, 역할, AWS API 작업 |
| 주요 설정 | 인바운드·아웃바운드 규칙 | IAM 정책 및 권한 |
| 적용 예시 | 특정 IP에서 SSH 접속 허용 | EC2 인스턴스 조회 및 생성 허용 |

Security Group에서 SSH 접속을 허용하더라도 IAM 권한이 없는 사용자가 AWS 리소스를 관리할 수 있는 것은 아니다. 반대로 IAM에 EC2 관리 권한이 있더라도 Security Group에서 네트워크 접근을 허용하지 않으면 외부에서 EC2에 접속할 수 없다.

따라서 안전한 운영을 위해서는 네트워크 접근 제어와 AWS 리소스 관리 권한을 각각 설정해야 한다.

## 2. Security Group 운영

### 2.1 인바운드 규칙

Security Group은 EC2 인스턴스에 적용되는 가상 방화벽이다. 외부에서 인스턴스로 들어오는 트래픽을 포트와 출발지 IP를 기준으로 허용한다.

현재 문서에 기록된 보안 그룹 설정은 다음과 같다.

| 유형 | 프로토콜 | 포트 | 소스 | 목적 |
|---|---|---:|---|---|
| HTTP | TCP | 80 | `0.0.0.0/0` | 외부 웹 서비스 접속 |
| SSH | TCP | 22 | `121.135.181.56/32` | 지정된 IP에서 서버 관리 |

HTTP 80번 포트는 웹 서비스를 외부에 공개하기 위해 전체 IP에서 접근할 수 있도록 설정한다. SSH 22번 포트는 관리 목적의 접속이므로 지정된 IP에서만 접근하도록 제한한다.

`0.0.0.0/0`은 모든 IPv4 주소를 의미한다. SSH나 데이터베이스 포트 등에 이 범위를 적용하면 외부의 불특정 다수가 접근을 시도할 수 있으므로 사용하지 않는다.

또한 `0-65535`와 같이 전체 포트를 허용하는 규칙은 생성하지 않는다. 서비스 운영에 필요한 포트만 개별적으로 허용하는 것이 원칙이다.

### 2.2 SSH 접근 IP 관리

SSH는 서버에 원격으로 접속하여 명령을 실행할 수 있는 관리 수단이다. 따라서 접근 가능한 출발지 IP를 제한해야 한다.

인터넷 연결 환경이 변경되면 기존에 허용했던 공인 IP가 달라질 수 있다. 이 경우 기존 SSH 규칙으로는 접속할 수 없으므로 다음 순서로 관리한다.

1. 현재 사용 중인 네트워크의 공인 IP를 확인한다.
2. AWS EC2 콘솔에서 인스턴스에 연결된 Security Group을 확인한다.
3. 인바운드 규칙에서 SSH(22)의 소스 IP를 현재 공인 IP의 `/32` 대역으로 변경한다.
4. SSH 접속을 확인한다.
5. 작업이 끝난 뒤에도 SSH 소스 범위가 불필요하게 넓어지지 않았는지 확인한다.

`/32`는 하나의 IPv4 주소만 지정하는 CIDR 표기법이다. 예를 들어 `121.135.181.56/32`는 해당 IP 하나만 허용한다.

SSH 접속 문제를 해결하기 위해 일시적으로 `0.0.0.0/0`을 설정했다면 작업 후 반드시 원래의 제한된 IP 범위로 되돌려야 한다.

### 2.3 아웃바운드 규칙과 트래픽 흐름

아웃바운드 규칙은 EC2 인스턴스에서 외부로 나가는 트래픽을 제어한다.

Public Subnet에 위치한 EC2가 인터넷으로 통신하려면 다음 조건이 필요하다.

- Public Subnet의 Route Table에 `0.0.0.0/0 → Internet Gateway` 경로가 있어야 한다.
- EC2에 퍼블릭 IPv4 주소가 할당되어 있어야 한다.
- Security Group 아웃바운드 규칙이 필요한 외부 통신을 허용해야 한다.

예를 들어 EC2에서 `curl https://example.com`을 실행하면 인스턴스에서 외부로 HTTPS 요청이 전달된다. 이때 라우팅과 아웃바운드 규칙이 정상적으로 구성되어 있어야 한다.

## 3. IAM 최소 권한 운영

### 3.1 최소 권한 원칙

최소 권한 원칙(Principle of Least Privilege)은 사용자나 역할에 업무 수행에 필요한 최소한의 권한만 부여하는 보안 원칙이다.

예를 들어 VPC와 EC2를 구성하는 실습에서 AWS의 모든 서비스를 관리할 수 있는 관리자 권한을 부여할 필요는 없다. 필요한 작업 범위에 맞춰 EC2, VPC, Security Group 관련 권한을 제한하는 것이 바람직하다.

실습에서는 다음 기준을 적용한다.

- 루트 계정을 사용하지 않는다.
- 별도로 생성한 IAM 사용자 또는 Role을 사용한다.
- EC2, VPC, Security Group 구성에 필요한 작업 중심으로 권한을 부여한다.
- 실습과 관계없는 S3, RDS 등의 서비스 권한은 부여하지 않는다.
- `AdministratorAccess`와 같은 전체 관리자 권한은 부여하지 않는다.
- 액세스 키와 시크릿 키를 저장소에 업로드하거나 코드에 직접 작성하지 않는다.

### 3.2 권한 설계 기준

IAM 정책을 설계할 때는 다음 작업을 기준으로 권한을 구분한다.

| 작업 범위 | 필요한 권한의 예시 |
|---|---|
| 네트워크 구성 | VPC, Subnet, Route Table, Internet Gateway 생성 및 조회 |
| 접근 제어 | Security Group 생성 및 규칙 관리 |
| 인스턴스 관리 | EC2 생성, 조회, 시작 및 종료 |
| 리소스 연결 | 네트워크 구성 요소와 인스턴스 연결 |
| 리소스 관리 | 실습 리소스에 태그 부여 및 조회 |

위 표는 필요한 권한의 범위를 설명하기 위한 설계 기준이며, 실제 IAM 정책의 세부 Action 목록이나 현재 부여된 권한을 증명하는 자료는 아니다.

### 3.3 권한 확인 및 문제 발생 시 대응

AWS CLI를 사용하기 전에는 현재 설정된 프로필의 IAM 신원을 확인한다.

```bash
aws sts get-caller-identity --profile vpc-lab
```

이 명령은 현재 인증된 AWS 계정과 IAM 주체를 확인한다. 액세스 키나 시크릿 키 자체를 출력하지 않는다.

신원 확인에 성공하더라도 모든 AWS 리소스를 조회하거나 관리할 수 있다는 의미는 아니다. 실제 작업 권한은 IAM 정책과 조직의 Service Control Policy(SCP) 등에 의해 추가로 제한될 수 있다.

현재 실습 환경에서는 `vpc-lab` 프로필의 STS 신원 확인은 성공했지만, IAM 주체에 EC2/VPC 조회 권한이 없고 서울 리전은 조직 SCP에서 차단된 상태로 기록되어 있다. 따라서 리소스 조회가 실패하더라도 이를 곧바로 AWS CLI 설치 오류나 인증 실패로 판단해서는 안 된다.

권한 문제가 발생하면 다음 순서로 확인한다.

1. `aws sts get-caller-identity`로 현재 인증 주체를 확인한다.
2. 실행한 명령에 필요한 IAM 권한이 있는지 확인한다.
3. 조직 SCP 또는 리전 제한이 적용되어 있는지 확인한다.
4. 필요한 작업에 한해 권한 관리 담당자에게 추가 권한을 요청한다.
5. 작업이 끝난 뒤 불필요한 권한이 남아 있지 않은지 검토한다.

권한이 부족하다는 이유만으로 `AdministratorAccess`를 부여하는 방식은 사용하지 않는다.

## 4. 자격 증명 관리

AWS CLI 자격 증명은 저장소와 분리하여 관리한다.

프로필 설정은 다음 명령으로 진행한다.

```bash
aws configure --profile vpc-lab
```

자격 증명 파일은 일반적으로 사용자 홈 디렉터리의 `~/.aws/credentials`에 저장된다. 이 파일과 설정 파일은 Git 저장소에 포함하지 않는다.

또한 다음 사항을 준수한다.

- 액세스 키와 시크릿 키를 소스 코드에 하드코딩하지 않는다.
- `.env`, `credentials`, 개인 키 파일을 Git에 커밋하지 않는다.
- 공개 저장소나 공유 문서에 자격 증명을 게시하지 않는다.
- 키가 노출되었다면 해당 키를 비활성화하거나 폐기하고 새 키를 발급한다.
- MFA가 필요한 환경에서는 승인된 세션 자격 증명을 사용한다.

## 5. 보안 점검 체크리스트

실습 전후에 다음 항목을 확인한다.

- [ ] 루트 계정이 아닌 IAM 사용자를 사용한다.
- [ ] `AdministratorAccess`를 사용하지 않는다.
- [ ] 현재 IAM 신원이 의도한 계정과 일치하는지 확인한다.
- [ ] SSH(22)의 소스가 지정된 IP로 제한되어 있다.
- [ ] HTTP(80)만 외부 공개가 필요한 서비스 포트로 허용한다.
- [ ] `0.0.0.0/0`에 전체 포트를 허용하지 않는다.
- [ ] 불필요한 인바운드 규칙이 없다.
- [ ] 자격 증명과 개인 키가 Git 저장소에 포함되지 않았다.
- [ ] 실습 종료 후 불필요한 접근 권한과 규칙이 남아 있지 않은지 확인한다.
